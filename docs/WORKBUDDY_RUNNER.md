# WorkBuddy 连续处理入口

这是 WorkBuddy 的持续运行规程，不是后台服务，也不替代指定外部 Chrome。
启动后保持同一个 WorkBuddy 任务和同一个外部 Chrome 工作标签，直到任务完成、暂停或用户停止。

## 启动前

1. 读取 `PROJECT_RULES`、`WORKER` 和 `AGENT_ADAPTERS`。
2. 在指定外部 Chrome 打开登记的 Gemini Notebook，核对账号、Notebook 名称和 URL。
3. 读取完整页面，并完成一次无副作用交互；失败就停止，不启动队列。
4. 运行频道范围的 `status`，确认全局暂停、频道暂停和频道租约。
5. 继续已有 run；没有可继续的 run 时，按用户已确认的模式执行 `begin`。

## 持续循环

对当前 run 重复以下流程：

1. 使用 `prepare RUN` 领取一条视频。
2. 按 `WORKER` 的节流规则，在同一个外部 Chrome 聊天中发送视频 URL 和“总结”。
3. 等待并读取页面。不能把点击成功或命令返回当成发送成功。
4. 页面显示完整总结后，登记 `summary`，按登记的标题格式改名。
5. 在当前页面核对完整总结、原视频链接、标题、账号和 Notebook，登记 `verify`。
6. 只有核验成功或按规程明确延期后，才领取下一条。
7. 收到 `daily_due` 时，先结清当前视频，再按 `handoff` 返回的 run 处理每日增量，完成后回到历史 run。

循环中必须遵守：

- `ready:false` 时只等待返回的秒数，不操作网页。
- 未知提交、账号异常、验证码、`/sorry`、配额和无法确认归属时立即暂停并 cleanup。
- 不重复发送未知状态的消息，不自动清除暂停，不自动补做所有延期项。
- 每20条按 `WORKER` 休息至少90秒；健康冷却按规程执行。
- 扩展归档运行期间不发送新的 Gemini 消息。

## 退出

- 队列完成：运行 `report`，确认 `complete=true` 后安全结束。
- 暂停或用户停止：保留现场，执行 `cleanup RUN`，报告未确认和延期项目。
- 需要历史改名：先停止新的 Gemini 操作，再启动 `history-rename serve RUN`；扩展完成后再核对报告。

WorkBuddy 应把这个文件作为连续任务的工作提示使用。它不能绕过登录、验证码、配额、人工确认或浏览器能力检查。

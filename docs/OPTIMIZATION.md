# 效率检查与修改记录

日期：2026-10-27。范围：队列、CLI、元数据采集、续跑、自动化入口、网页规程及现有测试。未修改 vendor 上游参考扩展，因为实际工作器不使用它。

| 检查发现 | 已修改 |
| --- | --- |
| arm、attach 等每次回传整条任务，重复标题、链接、时间戳和标识 | 默认返回精简确认；准备项只给当前阶段所需字段，--verbose 保留诊断信息 |
| next、metadata、summary、renew 分散调用 | prepare 合并领取/检查；summary/verify/defer 的 --next 提交当前状态后准备下一条；状态命令自动续租 |
| 重试 reserved 会重新联网查相同元数据 | 一小时内复用核实结果；标题变化、过期或 defer 会使缓存失效；仅有清单日期不能 arm |
| 日常增量也遍历全部历史分页 | 各类先查最新50条；末尾10条均已登记则结束，否则全量；周一全量，同日已成功扫描的定时续跑不重扫 |
| 历史持续持锁可能挡住每日增量 | prepare 在安全边界返回 daily_due；park 保留已生成聊天并让出队列，增量完成后继续历史 |
| 下一条元数据失败可能遮蔽上一条成功 | --next 分别返回 completed 与 next；上一条提交记录保留，下一条失败不要求重做上一条 |
| 暂停/忙碌唤醒也先读长规程 | 先用精简 status 判断，可推进才读 WORKER，每轮只读一次 |
| 数据库路径错误可能创建空库 | 除显式首次 add 外，缺失数据库直接报错，不自动建替代库 |
| 原有查询缺少队列索引 | 增加 owner/state 与 history/state 索引；保留现有记录 |

## 可核验的结果

- 52项自动测试通过：包含22条生成后统一核验、旧库原位升级、元数据缓存失效、增量窗口回退、续跑不重复扫描、过期锁拒绝写入、补做每日增量、合并命令失败恢复与原防重发测试。
- 对同一组虚构标题/链接的历史生成流程做本地输出比较：旧流程每条6次命令（next、metadata、arm、attach、summary、renew），新流程稳定运行时3次（arm、attach、summary --next；首次另需 prepare）。CLI输出从2956字符降至651字符，减少约78%。不包含浏览器页面、工具定义、模型推理或对话上下文，不能当作总 token 降幅或整体速度提升。
- 真实公开元数据读取：五岳散人 videos 页的50条窗口返回成功，频道ID匹配，用时约4.14秒。未下载视频、字幕或音频，未把读取结果写入任务库。未测同条件全量耗时。
- 网页规程改为复用浏览器与定位，只读当前相关区域；有完成条件则等待该条件，否则约10–20秒检查，不反复密集读取整页。此部分尚未做连续吞吐对比。

## 限制

- 窗口扫描依赖通常的最新排序，窗口外重新公开/延迟入库的视频可能到下一次周一全量扫描才发现。
- 缓存有效期内视频标题或公开状态仍可能变化；实际 Gemini 读取失败不能标成成功，可用 metadata --force 重新核对。
- Gemini生成等待、额度和网页稳定性仍影响总速度；没有证据支持某个固定提速倍数。
- 上述 2026-10-27 检查时尚未增加多聊天同时提交；后续历史任务改为同一标签连续提交多个独立会话，具体流程以当前工作器规程为准，实际吞吐尚未重新测量。

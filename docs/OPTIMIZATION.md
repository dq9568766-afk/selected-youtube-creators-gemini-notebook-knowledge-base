# 效率检查与修改记录

## 2026-11-12 每日增量最终优化

每日增量改为由 Codex 内置浏览器插件控制 Gemini，确认账号 `dq9568767@gmail.com` 后按频道串行处理。调度只读取 canonical 数据库中的 `tracking=1`、北京时间05:00后且当天未完成的频道；预检不排除暂停或租约。每个频道仅导航到数据库登记的 Notebook URL，不再执行 Notebook 完整页面读取、无副作用交互或独立 `status`。

定时增量不再要求历史首轮完成。`begin` 在同频道已有历史租约时原子接管：`reserved` 退回 `pending`，`submitting` 标记为 `uncertain/unknown_submit`，保留旧 run 记录并建立新的增量租约。旧 worker 下一次租约检查时停止；未知提交不自动重发。全局租约和暂停保护仍有效，其他频道租约不阻塞当前频道。

本次变更同步更新每日自动化提示、平台适配和工作器规程。历史任务仍使用原有历史队列规则；仅每日增量改为内置浏览器插件路径。

定时增量扫描成功后只处理该 run 首次发现的新视频。新增 `run_candidates` 保存候选视频，避免把旧的 `history=0` 遗留项混入每日轮次；无候选时可直接结束本轮。

增量报告也按当前北京时间当天的 scheduled run 候选统计；数据库恢复或旧版本留下的 `history=0` 遗留量单独显示为 `legacy_backlog`，不再冒充当日新增。

新频道规则同步确定：先在已登录且核验过账号的 Gemini 页面创建并登记真实 Notebook URL；`notebook CHANNEL_ID NOTEBOOK_URL` 登记成功即设置 `tracking=1`，不等待历史首轮完成。历史扫描与每日增量可以独立运行，仍受 `initialized`、暂停、租约和扫描成功保护。

## 2026-11-10 历史全量分类与日期任务快照

实践中发现两个容易相互放大的问题：频道已经初始化后再次执行历史全量扫描时，既有视频会沿用 `history=0`；日期补齐任务又会复用旧的两条视频快照。结果是大量历史视频被报告为新增，日期补齐也只覆盖旧快照。

已收敛为以下规则：

- 只有带 `mode=history` 且明确 `full` 的扫描才会把当前成功清单中的既有视频重分类为 `history=1`；增量扫描保持新ID为 `history=0`。
- `metadata-backfill` 启动时比较最新任务的条目数与当前历史视频数。历史集合扩大时创建新任务，并复用仍有效的日期缓存，不复用旧快照作为完整结果。
- 日期补齐前先结束持有频道租约的历史 run；补齐完成后只报告结果，不自动重新启动 Gemini 总结。
- API Key 的 `present` 只表示配置存在，不表示有效。若当前进程的 Key 被更新前的旧任务继承，且官方接口返回无效/过期，必须读取 `HKCU\Environment`，在新子进程中单独验证；验证成功后本轮命令显式注入该候选值。密钥值不进入输出、数据库或仓库。

本次回归验证覆盖历史 run 全量扫描对既有视频的重分类，`publish_check.py` 通过。

## 2026-11-09 数据库防丢失收敛方案

结论：继续使用一个 canonical SQLite 数据库，不按频道拆库。频道拆库会把租约、账号节流、暂停和跨频道调度分散，不能解决误写、错库或恢复覆盖，反而增加恢复入口。

本次只补三个保护：

- 每次打开任务库都校验 SQLite 完整性和固定的应用标识；校验失败或打开了其他 SQLite 文件时拒绝写入。
- 统一设置 busy timeout、WAL 和外键约束，让并发读取可以继续，写入由 SQLite 串行化；维护操作不再依赖复制 `.sqlite3` 文件。
- 增加 `db-check --backup PATH`，使用 SQLite 在线备份接口生成包含 WAL 状态的一致副本，并立即校验副本。

日常规则只保留一条：所有频道共用 canonical 数据库，任何维护或恢复前先停止任务写入，再执行 `python ytg.py db-check --backup <新备份路径>`。禁止直接复制主库、WAL 或 SHM 文件，也禁止用备份覆盖正在运行的主库。发现完整性失败时只读检查和恢复，不继续队列写入。

## 限制

- 窗口扫描依赖通常的最新排序，窗口外重新公开/延迟入库的视频可能到下一次周一全量扫描才发现。
- 缓存有效期内视频标题或公开状态仍可能变化；实际 Gemini 读取失败不能标成成功，可用 metadata --force 重新核对。
- Gemini生成等待、额度和网页稳定性仍影响总速度；没有证据支持某个固定提速倍数。
- 曾采用同一标签连续提交多个独立会话；2026-10-28 文档策略改回单标签串行、共享访问间隔及批次休息，以当前工作器规程为准。策略降低拦截概率的效果尚未实测。
- Google `/sorry` 表示异常流量拦截，不能据此确认唯一根因或可靠恢复时间。共享网络、VPN 流量也可能相关，见 [Google 官方说明](https://support.google.com/websearch/answer/86640?hl=en)。

## 2026-10-30 生成等待简化

- collect-first 改为每次提交后20秒检查一次。首次无正文且原消息、聊天、归属与停止状态均已确认，才可使用retry登记后在同聊天再尝试一次：先切换到另一个指定模型，再点击已发送消息中的“修改提示”，在“总结”前加“请”或去掉“请”后提交修改版本；不能从输入框原样重发。第二次再等20秒，仍未完成则停止并延期。首次已有正文但未完成不重发。
- 重试次数持久化，不搜索、不创建重复聊天、不自动补做延期项。未知提交、内容失败和页面中断不触发快速重试；停止及恢复失败仍按WORKER暂停。
- 同条快速重试可豁免常规15秒/恢复期180秒提交间隔；不同视频间隔现为15秒。访问节流、每20条休息及健康冷却保留。增量arm和retry各占一次每日提交预算，strict保持原规则。
- 113项隔离测试通过，发布检查及实际变更路径检查通过；未验证20秒方案的网页成功率或实际吞吐提升。

## 2026-10-31 Gemini UI 节流门控

- 普通 Gemini UI 动作共享任务数据库中的账号级时间槽，动作间隔至少15秒；不同视频提交间隔同步缩短为15秒。非提交动作使用 `pace access`，`arm`/`retry` 原子领取提交槽；未到时间返回剩余秒数且不改变视频状态或预算。

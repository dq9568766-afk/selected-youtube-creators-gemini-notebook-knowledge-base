# DQ 指定 YouTube 创作者视频知识库

## API 配置防误报

Windows 环境变量可能在当前任务进程启动后才更新。读取 `YOUTUBE_DATA_API_KEY` 时必须先看当前进程环境变量，再回退到当前用户的 `HKCU\Environment`；不能只检查 `os.environ` 就报告 API 缺失。`python ytg.py preflight --channel CHANNEL_ID` 会给出 `youtube_data_api.configured/source/key`，只显示是否存在，不输出密钥。若当前进程已有候选值但官方 API 返回密钥无效或过期，必须再单独读取 `HKCU\Environment`，在新子进程中用该值验证一次；验证成功后，运行补齐命令时要显式注入 Windows 用户变量，不能让旧进程值覆盖它。候选配置仍须用官方 YouTube Data API 实际请求验证；401/403、配额和网络失败按 `docs/WORKER.md` 处理。

This skill describes a portable workflow. The repository's `ytg.py`, `AGENTS.md`, and `docs/WORKER.md` provide the project-specific queue rules. Platform-specific installation and capability mapping are in `docs/AGENT_ADAPTERS.md`.

## Product meaning

“Gemini Notebook” means the native Notebooks feature inside the Gemini website. It does not mean NotebookLM or a local note-taking application.

## First-run archive naming choice

Before the first video is summarized for a channel, ask the user to choose one archive title format and remember that choice for later runs of the same channel:

1. Keep the original video title.
2. Topic category + original video title.
3. Publication date + topic category + original video title.

Use the exact original title. Ask for a concise topic category during each video’s summary only for choices 2 and 3. Choice 1 must not require topic generation. For choice 3, publication dates must come from verified metadata; if a date is unavailable, ask whether to process that video without the date or defer it. Never infer a date. Before starting a choice-3 run, tell the user that dates are not currently a guaranteed inventory field and explain the official YouTube Data API prerequisites in `docs/WORKER.md`. Do not ask the user to paste an API key into chat; use a local secret/configuration mechanism. If the key/API is not configured, leave date collection unstarted and offer choices 1 or 2 as alternatives.

For choice 3 on a new channel, remind the user that the verified local YouTube Data API configuration used by earlier channels will be reused if present, and ask the user to confirm that reuse. Read the existing local configuration through the approved local mechanism; never print or transmit the key. If no valid local configuration exists, do not start date collection and offer choices 1 or 2. After the inventory exists, date-topic history must pass the date-backfill gate before any Gemini summary is submitted.

Do not silently impose a naming format on first launch. Existing channel preferences remain in effect unless the user explicitly asks to change them.

## First full history scan: membership scope

Before a channel's first full historical scan, ask whether the user has an active YouTube membership for that channel. Remember the answer per channel and reuse it for later history and incremental scans; do not start the scan until the scope is known. If the user has no membership, exclude members-only videos like Shorts: do not scan, enqueue, or count them in history completion. If the user has membership, include them in the normal workflow. Membership access does not override the metadata and browser restrictions below; never infer inaccessible IDs or use cookies, private interfaces, or media downloads. Report the selected scope and exclusions clearly.

## Downstream use in NotebookLM

The queue currently stores verified video summaries in Gemini Notebook chats; it does not automatically sync or migrate them into NotebookLM. After the user imports or organizes those verified summaries as NotebookLM sources, the collection can be used as a reusable research and learning library. Benefits include:

- **Ask across a creator's archive:** query many imported summaries together to find recurring themes, arguments, examples, changes over time, or differences between videos, without reopening every chat.
- **Answers tied to sources:** NotebookLM grounds chat responses in selected sources and provides citations or source links so the user can inspect the supporting passage. This improves traceability; it does not guarantee correctness, so check the cited source and original video for important claims.
- **Control the evidence set:** select or exclude sources for a question, such as comparing only a particular period or topic, and add other relevant materials when needed.
- **Reuse insights in different forms:** create supported study or briefing guides, FAQs, reports, mind maps, flashcards/quizzes, and audio or video overviews where those features are available. These formats make the same archive easier to review, learn from, present, or listen to.
- **Build cumulative understanding:** add newly verified summaries over time and revisit earlier conclusions alongside new material, making it easier to track a creator's positions, recurring concepts, and developments across an archive.
- **Reduce repeated manual review:** use topic or timeline questions to narrow down which source videos deserve a closer watch, then follow the NotebookLM citation/source back to the relevant material.
- **Combine complementary sources:** compare the creator's summaries with articles, reports, notes, or other selected sources in one notebook, while keeping responses traceable to their inputs.
- **Support sharing and collaboration:** where the account and current NotebookLM sharing settings allow it, share a notebook or generated study material with collaborators for joint review.

These are downstream capabilities, not queue guarantees. Feature availability, source limits, sharing controls, and generated outputs can change. NotebookLM can omit context or make mistakes; its generated audio, video, reports, and answers are aids for exploration, not substitutes for the original source or independent fact-checking. This workflow must not claim that summaries are already present in NotebookLM unless their import and source association have been verified there.

## Queue policies

Read AGENTS.md and docs/WORKER.md before queue work. WORKER is the authoritative detailed procedure; its policy-specific rules govern recovery and deferral.

- For an authorized collection that tolerates individual failures, use channel-scoped `--policy collect-first` in history and incremental modes. Default CLI policy remains strict. Persist and reuse the policy when reopening a run.
- collect-first does not search. After each submission, check once at 20 seconds; only a confirmed, stopped, bodyless first attempt may be tried once more in the same chat through the guarded retry step. Before retrying, switch between “3.5 Flash-Lite极速回答 推理中” and “3.8 Flash全方位帮助” to the other model, then use the sent message's “修改提示” action and change “总结” to “请总结” or vice versa before submitting. Reuse complete historical metadata; defer missing metadata, generation timeout, unconfirmed submission, ambiguous chat, content failure, and archive verification failure, preserving evidence. Do not requeue deferred items automatically; this single in-chat retry before deferral is the only first-pass exception.
- In collect-first, check once 20 seconds after each submission, counting page-operation time. If the first confirmed request has no body, stop and confirm; if the page has not navigated or been interrupted, select the other listed model, verify the selection, record retry intent, click “修改提示” on the sent message, adjust the wording, and submit the edited prompt. Do not resend the same prompt from the input box. The WORKER specifies evidence for attached and addressless states. If the page navigated, the submission is unknown, or account/Notebook membership or model selection is unclear, do not edit or submit again. Attach a stable chat URL when available; a completed response without an identifiable address is deferred as chat_unidentified, not counted as success. Partial unfinished output is stopped and deferred without retry; after the second check, stop and defer unfinished output. Strict timing remains unchanged.
- Login, CAPTCHA, `/sorry`, quota, and a confirmed browser/session outage are global blockers. Item submission uncertainty, source unavailability, and health-probe failures are recorded against the affected channel; they do not block an independently scoped channel. Transient network/browser failures get only the bounded recovery described in WORKER.
- When Gemini shows a quota/rate-limit or CAPTCHA block, record it through the guarded `pause quota` or `pause captcha` command. The local database stores only queue/send metadata for later analysis; use `gemini-limit-report` before recovery. Never store prompt text, summaries, transcripts, page text, cookies, or tokens.
- In history and normal incremental runs, finish each video before the next: generate, rename immediately, then verify exact title, complete summary, original video URL, account and Notebook on the current page. If a collect-first incremental submission becomes unknown, the state machine records `submission_unconfirmed` as a deferral and permits the next reservation; the next submission must use a fresh blank chat in the same registered Notebook, never the unknown chat, and the unknown item is never resent automatically. Strict runs and history retain the conservative serial unknown-submit pause. Use `current-page-video-summary` evidence for normal verification. In extension archive mode, the extension performs the page navigation, title change, reopen and verification itself; it retries a recoverable page failure at most twice, then preserves pending evidence for manual review. A persistent reopen flag forbids current-page verification. No routine reopening or sampling is required. `step ... summary --next` returns the current archive task; `step ... verify --next` advances only after successful verification. `finalize RUN` remains available for unfinished archives.
- A verified video or explicitly deferred video counts once toward the shared account pace in both modes. After 20 processed items, rest for at least 90 seconds before the next video; timing starts when item20 is settled and survives restarts and round changes. Gemini UI actions and different-video submissions are at least 15 seconds apart; use `python ytg.py pace access --run RUN` before non-submission actions, while `arm` and `retry` enforce the submission gate. The account coordinator covers only the short page-action window; different channels may remain in Gemini generation concurrently, while their page actions and submissions pass through the shared gate. Respect the single working tab, serial processing, pacing, lease ownership, and the registered Notebook. Do not create public share links to discover chat URLs or substitute another Notebook without evidence.

Collect-first incremental unknown submissions are item-level `submission_unconfirmed` deferrals and do not pause the channel, but they still require a fresh blank Notebook chat before the next submission. Metadata limitations alone are item-level outcomes in both modes.

An explicit user recovery request allows one recovery procedure for the affected scope, not a second confirmation loop. Release this worker's lease/reservations through cleanup while preserving pause and unresolved evidence.

Keep one Goal per channel, with scope and completion criteria from WORKER. Do not inspect context usage or create a new chat because of automatic compaction; continue the Goal in the current chat. Chat handoff occurs only when the user explicitly requests it and follows WORKER. Daily incrementals do not create parallel chats, but a collect-first incremental may continue after an isolated unknown submission by opening a fresh blank chat in the same Notebook; it must not reuse or resend the unknown chat. Strict/history serial protections remain. Exclude Shorts from both history and daily scans, and report them as excluded rather than treating their absence as a complete inventory. Daily scans use the recent window only when its earliest known publication date reaches the previous successful scan boundary; otherwise they expand to a full tab scan. Treat `complete` as tab-operation success only; use the scan's separate date-coverage result to distinguish `full`, `mixed`, `recent-window`, and `partial`. After an explicit user resume, settle each item and immediately claim the next with --next; do not pause/cleanup per video. Daily incrementals have a persistent per-channel budget of20 submission intents per local day; history has no daily count cap. A once-daily automation lists due tracking=1 channels after local 05:00 without filtering pauses or leases, then starts work serially. It may start a channel incremental while that channel has unfinished history; a scheduled incremental atomically takes over a same-channel history lease and marks in-flight submissions unknown. Global leases and service pauses remain in force, and unknown submissions are never automatically resent. Use the daily-candidates precheck and follow WORKER for scan completeness, budget outcomes and recovery.
- Historical processing uses one persistent agent task objective per channel. It covers only the channel's scanned historical videos and remains active until every such video is verified, explicitly deferred, or placed in manual review, with archive backlog cleared. Daily incrementals are outside this objective; registering a verified Notebook enables tracking before the history report is complete, so unfinished history may coexist with an independent scheduled incremental. After history completion, a daily_due handoff may park history, complete the incremental run, and return to the same historical objective. A chat handoff continues that objective and does not require the user to restart it. Channel chats and daily incrementals use GPT-5.6 Luna with low reasoning effort.
- Completion requires the channel-scoped history report with complete=true after all items are verified or explicitly deferred and finalization backlog is cleared. Report actual generated, verified, not-generated, success rate and every deferred item. No unverified item counts as success; manual retries wait for a separate user request.
- The CLI is not a background worker. Only claim progress while browser/queue work is actively executing. Keep summaries and final review lists in Gemini/chat, not local files. Releasing a lease is a lifecycle action, not a per-video step: use `cleanup` when stopping, pausing, entering a documented cooldown, or handing work back; keep the lease while continuously processing the next item.


## 历史日期补齐（按标题格式决定是否为总结前置条件）

日期补齐是独立维护任务。王志安当前规则要求聊天标题包含发布日期；日期必须来自已核实元数据，缺日期的视频延期并列入补齐/人工复核清单，不猜测日期。其他频道仍按各自登记规则执行。

`date-topic` 是历史总结的日期前置条件；`history-pipeline` 可以在用户明确启动该标题流程时运行日期补齐，独立的 `metadata-backfill` 命令仍只在用户明确要求日期资料时使用。日期补齐不发送 Gemini，也不自动重新入队延期总结。完成时必须报告用户可开始历史总结，并列出覆盖率与异常数量；用户明确开始后先创建/恢复本频道 Codex Goal，再按 WORKER 的浏览器门槛启动队列。日期补齐完成后，聊天标题回改是单独的、逐聊天可核验的维护步骤。每日增量自动化使用 Codex 内置浏览器插件，确认目标账号后按登记 Notebook URL串行处理。

元数据请求使用共享数据库节流，默认初始间隔1秒，可由 YOUTUBE_METADATA_INTERVAL_SECONDS 配置，跨进程和重启保留；不再按请求计数强制等待300秒。官方 Data API 元数据请求按每批最多50个视频ID合并。429自动指数退避，连续成功后逐步恢复到配置间隔；认证挑战和网络故障仍立即暂停。配额耗尽记录官方太平洋时间下一个午夜，在重置前不清除。此暂停不表示Gemini登录失效。用户明确恢复后使用 metadata-backfill resume --confirmed 清除元数据服务暂停；不清除其他范围暂停，不自动唤醒。普通扫描和单条查询也遵守此访问门槛。

补齐状态与总结状态分离：pending/fetching/complete/unavailable/review；每条事务保存，失败保留待处理。明确限制或确实没有公开日期记unavailable，未知异常或身份冲突停止复核。保留release_date、upload_date、采用来源和检查时间，不推算日期。补齐不发送Gemini、不重新入队延期总结，不改已有聊天名称。频道租约互斥，退出释放本轮占用。

报告区分补齐首轮结束与全部日期齐全：complete表示无pending/fetching/review；all_dates_complete及date_coverage说明实际覆盖率。不可用项目不算日期成功。此专用模式实现共享节流与持久暂停，取代旧文档中“暂未实现共享限速”的描述；普通总结流程仍不批量预取。
